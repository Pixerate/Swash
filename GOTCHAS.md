# Gotchas & Known Pitfalls

## 1. Sandbox Permissions for `xcodebuild` and `git`
- **Issue**: Standard sandboxed execution can block read/write operations to Developer directory caches (`~/Library/Developer/Xcode/DerivedData`, `/var/folders/.../C/clang/ModuleCache`) and user git configuration (`~/.gitconfig`), resulting in `Operation not permitted (error code 1 / 257)`.
- **Solution**: Execute build commands (`xcodebuild`) and git operations with appropriate permissions (`BypassSandbox: true` where needed) to ensure access to Xcode toolchains, standard SDKs, and git configs.

## 2. Headless AppKit & SwiftUI Snapshot Rendering
- **Issue**: Calling `cacheDisplay(in:to:)` on an `NSView` or `NSHostingView` before layout completes or without setting a frame size can produce empty 0x0 images.
- **Solution**: Set an explicit frame on `NSHostingView` (or compute `fittingSize`), call `layoutSubtreeIfNeeded()` and `displayIfNeeded()`, and create an `NSBitmapImageRep` matching the view bounds.

## 3. Changeset Requirements
- **Issue**: Missing changeset files cause CI failures on pull requests and commits.
- **Solution**: Every PR and task must include a changeset file in `.changeset/<unique-name>.md` created via `npx changeset` or by writing the markdown file directly.

## 4. Main RunLoop in Headless CLI Test Runners
- **Issue**: Async main queue dispatches (such as `DispatchQueue.main.async` inside `updateNSView` or coordinator callbacks) do not execute in headless command-line tools without an active event loop.
- **Solution**: Pump `RunLoop.main.run(until: Date().addingTimeInterval(...))` before capturing snapshots or evaluating asynchronously updated view states.

## 5. Changeset Status Verification on `main`
- **Issue**: Running `npx changeset status --since=origin/main` when working directly on `main` before committing fails with `Error: Failed to find where HEAD diverged from "origin/main"` because HEAD has not diverged from origin/main yet.
- **Solution**: Manually verify that `.changeset/<unique-name>.md` conforms to the valid frontmatter format (`--- \n "swash": <type> \n ---`), or check status after creating local commits on a branch or relative to `HEAD~1`.

## 6. App Sandbox vs. Sibling Document Assets (Images) & Security-Scoped Bookmarks
- **Issue**: When `ENABLE_APP_SANDBOX = YES` is set on the main app target, macOS sandbox Powerbox only grants security access to the exact user-selected Markdown file, not its containing directory. Any relative asset links (such as `![Screenshot](Screenshot.png)`) fail to load at runtime because file reading (`isReadableFile`, `NSImage(contentsOfFile:)`) is denied by sandbox kernel rules, causing the editor to render placeholder badges instead of images.
- **Solution**: Re-enable App Sandbox on the main `Swash` target (`ENABLE_APP_SANDBOX = YES`) with user-selected file read/write and app-scoped bookmark entitlements (`com.apple.security.files.user-selected.read-write`, `com.apple.security.files.bookmarks.app-scope`). When unreadable relative image assets are detected in a document, display a prominent access banner with a "Grant Access…" button (and provide `File -> Grant Folder Access…` menu command). Present an `NSOpenPanel` targeting the document's directory so the user can grant folder access at runtime. Save the resulting security-scoped URL bookmark to `UserDefaults` and resolve/activate it via `startAccessingSecurityScopedResource()` on subsequent launches for seamless persistence across app restarts.



## 7. Driving the UI for Automated Testing (Bubble Menu, Editor Interactions)
- **Issue**: `osascript`/System Events UI scripting fails with `osascript is not allowed assistive access (-1728)` from agent shells. Walking the SwiftUI accessibility tree in-process (`NSHostingView.accessibilityChildren()`) also returns only an empty `AXGroup`, because SwiftUI populates its AX tree only when an assistive client is attached.
- **Solution**: Host the real views in-process (see `Tests/EditorAudit/`). Send `NSTextView` commands directly (`insertNewline`, `insertTab`, `deleteBackward`, `moveRight`, `undoManager.undo()`). For the bubble menu, `run_audit.sh` injects a `TestHooks` capture into a *copy* of `BubbleMenuView.swift` so the harness can invoke the exact closures the buttons call.

## 8. Spec Runner Overwrites Tracked Snapshots
- **Issue**: `./scripts/run_spec_tests.sh` writes PNGs directly into the git-tracked `Tests/GFMSpec/snapshots/`, so every run dirties ~100 files with byte-level differences.
- **Solution**: After a local run, restore with `git checkout -- Tests/GFMSpec/snapshots` unless the snapshots were intentionally regenerated.

## 9. Editor Text Storage Offsets ≠ Raw Markdown Offsets
- **Issue**: In styled ("Edit Text") mode, tables and images are collapsed into a single U+FFFC attachment character, so `NSTextView.selectedRange()` does not index into `document.text`. Applying a storage range to raw markdown edits the wrong span after an attachment.
- **Solution**: The `selectedRange` binding published by `SwashTextView` is **always in raw-markdown offsets**. Convert with `Coordinator.rawRange(forStorage:in:)` / `storageRange(forRaw:in:)` (backed by `AttachmentOffsetMap`). Never apply a raw range to the text storage, or a storage range to `document.text`, without mapping. Invalidate the cached map (`invalidateOffsetMap()`) whenever storage changes outside `textDidChange`.

## 10. Bubble-Menu Edits Must Go Through the Text View
- **Issue**: Assigning `document.text = …` from SwiftUI makes `updateNSView` reset `textView.string`, which bypasses `NSUndoManager`. The edit can't be undone, and selection and typing state are lost.
- **Solution**: Use `commitEdit(_:selection:actionName:)` in `ContentView`, which calls `SwashEditorController.apply`. That turns the rewrite into a minimal `shouldChangeText`/`replaceCharacters`/`didChangeText` edit on the live text view. Assign `document.text` directly only when no editor is attached.

## 11. `ObservableObject` Conformance Fails for Plain Helper Classes
- **Issue**: Declaring a property-less helper such as `final class SwashEditorController: ObservableObject` fails to build in this target (`does not conform to protocol 'ObservableObject'`).
- **Solution**: Don't make non-observable helpers `ObservableObject`. Hold the reference in `@State private var editor = SwashEditorController()`; `@State` keeps the same instance across view updates.

## 12. Code Detection Must Use `MarkdownParser.codeRanges(in:)`
- **Issue**: Ad-hoc checks (counting ``` lines, regexing backticks) miss `~~~` fences, indented code and multi-backtick spans. Calling them once per regex match made styling quadratic (27 s per keystroke at 2,200 lines).
- **Solution**: Compute `MarkdownParser.codeRanges(in:)` once per pass (one O(n) scan), then query it with `excludes(_:)`, `blockIntersects(_:)` or `spanContains(_:)` (binary search). `fencedCodeBlock(containing:in:)` locates the block around a selection.

## 13. `ObjectIdentifier` Keys Are Reused After Deallocation
- **Issue**: The Markdown parser keeps per-node side tables (block state, inline sources, text maps) keyed by `ObjectIdentifier`. When a node is discarded mid-parse (a paragraph absorbed into a setext heading, an emphasis delimiter run that was fully used), it can be deallocated and a new node allocated at the same address, which silently inherits the stale entry. Setext headings duplicated their text into the following paragraph until this was fixed.
- **Solution**: Side-table values must hold a strong reference to their node (`BlockState.node`, `(cell, source)`, `(node, map)`), so identifiers stay unique for the lifetime of the parse.

## 14. Command-Line Test Scripts Compile Explicit File Lists
- **Issue**: `scripts/run_spec_tests.sh`, `scripts/run_commonmark_spec.sh` and `Tests/EditorAudit/run_audit.sh` call `swiftc` with hand-picked source files. Moving a type into another file (for example `TableAlignment` and `AlertType` into `Swash/Markdown/MarkdownNode.swift`) breaks them, even though the Xcode build, which uses synchronised folders, still succeeds.
- **Solution**: After moving or adding source files, update the file lists in all three scripts. The Markdown engine is not in this repo any more: each script sources `scripts/pixerate_markdown.sh`, which builds the `PixerateMarkdown` module once and passes it as `$PIXERATE_MARKDOWN` (#63).

## 15. Xcode May Rewrite `project.pbxproj` When a New Source Folder Appears
- **Issue**: The first `xcodebuild` after adding `Swash/Markdown/` rewrote the synchronised-group membership exceptions (dropping `Swash.entitlements`), an unrelated project-file change.
- **Solution**: Check `git status` after builds and revert unintended `project.pbxproj` changes (`git checkout -- Swash.xcodeproj/project.pbxproj`). New files in synchronised folders need no project edits.

## 16. Test Key Handling Through `doCommand(by:)`, Not the Responder Methods
- **Issue**: Calling `textView.insertNewline(nil)`, `insertTab(nil)` or `deleteBackward(nil)` directly bypasses the `NSTextViewDelegate.textView(_:doCommandBy:)` hook, so Notion-style key handling (list continuation, indent, Backspace-unformat) appears not to work in tests.
- **Solution**: Send commands with `textView.doCommand(by: #selector(NSResponder.insertNewline(_:)))`. This is the path real key presses take via `interpretKeyEvents`. For shortcuts, send a synthesised `NSEvent.keyEvent` to `performKeyEquivalent(with:)`.

## 17. Menus That Block Must Be Injectable for Headless Tests
- **Issue**: `NSMenu.popUp(positioning:at:in:)` runs a modal tracking loop, so the "/" block menu and the code-language menu can't be exercised in the headless harness.
- **Solution**: Presentation goes through replaceable static closures (`SwashTextView.Coordinator.blockMenuPresenter`, `languageMenuPresenter`). Tests substitute a closure that "chooses" an item. The insertion logic itself lives in `MarkdownEditingCommands` and is unit-tested.

## 18. Backticks in Shell-Quoted Commit Messages
- **Issue**: A commit message passed with `git commit -m "…"` that contains triple backticks is treated by zsh as command substitution, and the whole command line fails to parse ("unmatched").
- **Solution**: Write the message to a file and use `git commit -F <file>`, or avoid backticks in `-m` messages.

## 19. CI Builds With an Older SDK Than Local Xcode
- **Issue**: CI (`PR Build`, `Build & Release`) runs on `macos-26` with `latest-stable` Xcode, which can lag the local Xcode (a beta or newer release). AppKit signatures can differ between SDKs: `NSTextBlock.drawBackground(withFrame:in:characterRange:layoutManager:)` takes `NSView` on one SDK and `NSView?` on another, so an override that compiled locally broke the v1.5.0 release on `main`. Until v1.8.4, CI ran on `macos-14` (macOS 15.2 SDK), which was older than the 15.7 deployment target and logged deployment-target warnings on every build.
- **Solution**: Avoid overriding AppKit methods whose signatures have changed between SDKs, and prefer composition (here, `SwashLayoutManager` paints `IndentedTextBlock.fillColor`). The `PR Build` workflow builds every pull request on the release toolchain, so these failures show up before merging. Keep the CI runner's SDK at or above `MACOSX_DEPLOYMENT_TARGET`. Since #65, `PR Build`, `Build & Release` and `Preview Screenshots` run on the `xcode-27` runner image with `xcode-version: '^27.1'`: iPhone Duo support (vertical bars, `ArrangementView`, `visibilityPriority`, `toolbarVerticalBehavior`) needs the iOS 27.1 SDK, and the `macos-26` image's newest Xcode is 26.6, whose SDK doesn't declare those APIs, so `#available` checks alone don't compile there. That image's simulator runtime identifiers can carry a suffix after the version (`…SimRuntime.iOS-27-2-iPhone19…`), so the workflows' simulator pickers sort on the leading numeric parts only.

## 20. Incremental Restyling: Raw Text vs Partially Collapsed Storage
- **Issue**: Edit Text restyles only the changed blocks. Outside that region the text storage still holds collapsed table and image attachments, so storage offsets differ from AST (raw-Markdown) offsets by a constant shift, and `storage.string` is not the Markdown.
- **Solution**: `MarkdownEditorStyler` reads `document.source` and writes to the storage through `valid(_:)` (`raw location − storageShift`). Never read text from the storage or write raw ranges directly in the styler. Any code that replaces the storage or changes styling inputs (flavor, base URL, folder access, external text) must set `forceFullRestyle = true`. The interaction harness's `incremental-*` cases compare every incremental result with a full restyle; extend them when adding block types.

## 21. Bundled Web Resources Are Flattened, and Offscreen WebKit Snapshots Need Care
- **Issue**: Files under `Swash/Rendering/` (KaTeX, Mermaid, `swash-render.html`) are copied flat into the app's and Quick Look's `Resources`, because synchronised groups do not keep sub-folders. KaTeX's stylesheet expects a `fonts/` folder. KaTeX also loads its fonts lazily, so `document.fonts.ready` can resolve before the size fonts (∫, large delimiters) are requested, and the first snapshot is missing glyphs. `WKWebView.takeSnapshot` returns images at the backing scale of the `snapshotWidth` you give in points; passing pixel widths gives 4× images. SwiftUI stacks squeeze resizable images unless they are given `.fixedSize(horizontal: false, vertical: true)`.
- **Solution**: Refresh the vendor files only with `scripts/update_render_vendor.sh`, which rewrites the font URLs and keeps only woff2. The page loads every `FontFace` up front and awaits it before measuring. `RichContentRenderer` uses `pageZoom = 2` and `snapshotWidth` in points. Headless tests set `SWASH_RENDER_RESOURCES` to `Swash/Rendering`; without it, the renderer reports unavailable and every view falls back, so the other harnesses are unaffected. In a sandbox, WebKit needs outgoing connections (`network.client`), so the Quick Look extension sets `ENABLE_OUTGOING_NETWORK_CONNECTIONS`.

## 22. Scroll Positions Must Not Go Through SwiftUI State
- **Issue**: Split view synced the two panes through an `@State` scroll offset in `ContentView`. Every scroll tick re-evaluated `ContentView`, which re-parsed the whole preview, rebuilt its view tree and re-measured it with `fittingSize`, so scrolling stuttered on longer documents.
- **Solution**: `ScrollSync` (in `MarkdownPreviewView.swift`) scrolls the other pane's clip view directly and stores the offset in a plain class held in `@State`, so the mode-switch position is kept without invalidating views. Don't publish per-frame values (scroll offsets, unchanged selection rects) to SwiftUI state. `MarkdownPreviewView` also caches its parse by text and flavor.

## 23. Nested Horizontal Scroll Views Latch Vertical Gestures
- **Issue**: AppKit sends a whole trackpad scroll gesture, momentum included, to the scroll view under the pointer when it begins. In the preview, tables and code blocks sit in SwiftUI `ScrollView(.horizontal)` views (backed by `NSScrollView`), so a vertical swipe that began over one stalled there.
- **Solution**: `NestedScrollRouter` (in `MarkdownPreviewView.swift`) is a local `.scrollWheel` monitor. It decides at each gesture's `.began` (or per event for mouse wheels) and sends mostly-vertical gestures that start over a nested scroll view to the preview's `NSScrollView`. The decision lives in `shouldForward(...)` so the interaction harness can test it without a real event stream.

## 24. Release Version Comes From the Build Command and Project File
- **Issue**: `MARKETING_VERSION` previously remained `1.0` in `project.pbxproj`, and only the release workflow passed `MARKETING_VERSION="$VERSION"` to `xcodebuild`. Builds run from Xcode and any local or non-release archives displayed version `1.0` in iOS Settings and the Mac About panel / Settings.
- **Solution**: In `.github/workflows/release.yml`, the "Commit Version Bumps & Repository Assets on Main Branch" step synchronizes `MARKETING_VERSION` in `Swash.xcodeproj/project.pbxproj` with the release version and commits it alongside `package.json` and `CHANGELOG.md`. Every target's `Info.plist` uses `$(MARKETING_VERSION)` and `$(CURRENT_PROJECT_VERSION)`. iOS Settings shows the marketing version and build number (`CFBundleShortVersionString (CFBundleVersion)`), so a local build is easy to tell from a release; the Mac's standard About panel already shows both.

## 25. "Metadata extraction skipped" Warnings From App Extensions
- **Issue**: Xcode runs `ExtractAppIntentsMetadata` for every Swift target. Extensions that don't link AppIntents (QuickLook, Share, Thumbnail) log `appintentsmetadataprocessor warning: Metadata extraction skipped, no AppIntents.framework dependency found` on every build, including CI. `LM_FILTER_WARNINGS = YES` (`--quiet-warnings`) does **not** silence it.
- **Solution**: Set `LM_SKIP_METADATA_EXTRACTION = YES` on those extension targets (Debug and Release) so the step doesn't run. Leave it unset on `Swash` and `SwashWidgetExtension`, which do use App Intents. A new extension that adopts App Intents must remove the setting, or Shortcuts won't see its intents.

## 26. Images Go Through `ImageCache`
- **Issue**: Loading and scaling images directly (`NSImage(contentsOfFile:)` plus `scaleImageForEditor`) in a styling pass or a SwiftUI `body` re-reads the file on every keystroke near the image and on every preview render.
- **Solution**: Resolve images with `MarkdownParser.resolveImageFile`, which checks candidate paths cheaply and loads through `ImageCache.shared`; scale with `ImageCache.shared.editorImage(_:path:maxWidth:)`. Entries are validated by modification date and size. Folder access is started once per folder per session by `FolderAccessManager.ensureAccess`; don't call `startAccessingSecurityScopedResource()` elsewhere.

## 27. Test Harnesses Compile `SwashTextView.swift` for macOS 14
- **Issue**: `run_audit.sh` (render, interact, perf) and `run_spec_tests.sh` build with `-target arm64-apple-macos14.0`, while the app targets macOS 15. macOS 15-only APIs such as the Writing Tools delegate methods (`textViewWritingToolsWillBegin`, `writingToolsIgnoredRangesInEnclosingRange`) break those builds even though Xcode succeeds.
- **Solution**: Mark macOS 15-only members of the shared editor files `@available(macOS 15.0, *)` (delegate methods can be declared this way), or guard calls with `if #available`.

## 28. The Bubble Harness Compiles `ContentView`'s Dependencies Explicitly
- **Issue**: `run_audit.sh bubble` compiles `ContentView.swift` with a hand-written file list. Any new type that `ContentView` uses (outline sidebar, document commands, quick note, conflict banner, document opening) has to be in that list, or the harness fails with "cannot find type".
- **Solution**: When `ContentView` starts using a new file, add it to the `bubble` `swiftc` line. Keep app-only machinery (Carbon hot keys, `SMAppService`, menu bar) in files that still compile outside the app.

## 29. Writing Tools Edits the Text Storage In Place
- **Issue**: Apple Intelligence Writing Tools rewrites `NSTextView` storage directly, with its own animation attributes. Restyling during a session (which replaces attributes, collapses tables and images into attachments, and pushes `document.text` and autosaves) fights it and can corrupt the rewrite. However, deferring publication without lifecycle flushes causes edits made during a session to be lost if the window closes, the app terminates, or views are dismantled before `textViewWritingToolsDidEnd` fires. Furthermore, if a session terminates abnormally without `textViewWritingToolsDidEnd`, `isWritingToolsActive` remains stuck, preventing subsequent typing from reaching the document.
- **Solution**: `Coordinator.isWritingToolsActive` is set between `textViewWritingToolsWillBegin`/`DidEnd`. While it is set, `highlightMarkdown` and `textDidChange` defer updates and record `textChangedDuringWritingTools`. On `NSWindow.willCloseNotification`, `NSApplication.willTerminateNotification`, and `SwashTextView.dismantleNSView`, `flushWritingToolsChanges()` commits any pending edits to `parent.text`. As a safety net, `verifyWritingToolsState(in:)` clears the session and flushes when `NSTextView.isWritingToolsActive` (macOS 15+) says it has ended. A key press is no sign it ended: Writing Tools has its own text fields. Code, math, HTML, front matter and attachments are reported as ignored ranges, in storage coordinates.

## 30. Untitled Documents With Initial Text
- **Issue**: `DocumentGroup` creates new documents from `SwashDocument()`, so there's no direct way to open an untitled document that already has text (quick notes, imports). Writing a temporary file and opening it makes Save write into the temporary folder.
- **Solution**: `NewDocumentSeed.createDocument(with:)` queues the text and calls `NSDocumentController.newDocument(_:)`. `ContentView.onAppear` takes the next seed when its document is untitled and empty.

## 31. macOS App Icon HIG Grid Dimensions & Drop Shadow
- **Issue**: Exporting app icons with generic or iOS squircle padding (e.g. 75% scale or 768px body with 128px margins on a 1024x1024 canvas) makes the icon appear ~6.3% smaller than surrounding apps in the macOS Dock and Launchpad. Additionally, macOS does not automatically synthesize dock drop shadows for custom icons, so icons without Apple's subtle downward drop shadow appear ungrounded and floating.
- **Solution**: Follow Apple's macOS Human Interface Guidelines (HIG) App Icon grid specifications: the squircle body must occupy 824 × 824 px centered on a 1024 × 1024 canvas (100 px margins top/bottom/sides, ~80.5% fill). Include the standard Apple HIG downward drop shadow (offset `dy = +10`, Gaussian blur `radius = 16`, opacity `~28%`) in the asset artwork so the icon sits seamlessly on the Dock shelf alongside native system apps.

## 32. SwiftUI Overlays Don't Change the Text View's Cursor
- **Issue**: The bubble menu is a SwiftUI `.overlay` drawn over the `NSTextView`'s scroll view, not an `NSView` with its own cursor rects. The text view keeps setting the I-beam, including over its 20 pt inset margins.
- **Solution**: `SwashNSTextView.overrideCursor(at:)` returns the arrow over the margins and over `bubbleMenuFrame` (in overlay coordinates, kept up to date through `SwashEditorController.bubbleMenuFrame`), and the pointing hand over checkboxes and footnote links. `mouseMoved` and `cursorUpdate` apply it. `BubbleMenuView` also sets the arrow with `onContinuousHover`.

## 33. Table Attachments Are Sized From Their SwiftUI Content
- **Issue**: `TableAttachmentCell` used to guess its height (36 pt per row). The hosting view then held content of a different height, so any state change (a cell entering edit mode, the header chevron appearing) moved the whole table. The edit cell (`NSTextView`) was also taller than the display `Text`, and had a different weight and alignment.
- **Solution**: The cell measures `hostingView.fittingSize` (cached per table data and width). Display and edit cells share `CellTextField.lineHeight`, and the edit cell copies the header weight and the column alignment. The column menu is always laid out and only hidden. Cell parses are cached (`InlineMarkdownText`), and `.cellSelectionDidChange` is posted only when the selection actually changes.

## 34. Custom Attributed-String Values Must Be `Hashable`
- **Issue**: Storing an `Equatable`-only Swift struct as an attribute value logs "Obj-C `-hash` invoked on a Swift value … that is Equatable but not Hashable", and attribute run coalescing gets slow.
- **Solution**: Make attribute value types (`FootnoteLink`, …) `Hashable`.

## 35. An `<img>` Alone on a Line Is an HTML Block
- **Issue**: CommonMark parses a line holding just `<img …>` as an HTML block (type 7), not inline HTML. The image menu writes exactly that when an image gets a width, and the editor used to show the tag as source.
- **Solution**: `MarkdownEditorStyler` turns an HTML block holding a single `<img>` into an image attachment, and `MarkdownFormatting.image(exactly:)` accepts both `htmlInline` and `htmlBlock` images.

## 36. `NSTextBlock` Background Expands Into `paragraphSpacingBefore`
- **Issue**: Setting `paragraphSpacingBefore` on an `NSMutableParagraphStyle` that contains an `NSTextBlock` causes AppKit's text system to include the leading paragraph spacing inside the text block's bounding rectangle. Consequently, the text block's `backgroundColor` fills the entire spacing area above the line, turning a 1-2 pt horizontal divider line (`thematicBreak`) into an unexpectedly thick (12+ pt) block.
- **Solution**: Keep `paragraphSpacingBefore = 0` (and `paragraphSpacing = 0`) on paragraph styles containing `NSTextBlock` dividers, and size the line via font height (`font = NSFont.systemFont(ofSize: 2)`) and line height metrics.

## 37. Edit Text Display String Isn't the Markdown
- **Issue**: Tables, images and (since 1.14.0) Mermaid blocks are replaced in the editor's text storage by an attachment character (`U+FFFC`), so `NSTextView.string` no longer equals the document. Tests that compared `tv.string` with the source started failing in `scripts/run_rich_render_tests.sh` once Mermaid became an attachment, and the PR build stayed red.
- **Solution**: Compare the Markdown written back through the editor's text binding (`box.text` in the harnesses), and find diagrams as `ImageTextAttachment`s (alt `"Mermaid Diagram"`) rather than `.richPreview` overlays.

## 38. `NSPrintOperation` Calls Back on Its Own Thread
- **Issue**: `DocumentExporter` prints a `WKWebView` with `runModal(for:delegate:didRun:contextInfo:)` (`run()` gives blank pages). With no panel shown, AppKit calls the `didRun` selector on the print operation's thread, not the main thread. Under default main-actor isolation, touching the window there crashed with `EXC_BREAKPOINT` in `WKWindowVisibilityObserver`.
- **Solution**: Declare the callback `@objc nonisolated` and hop to the main queue before touching the web view, window or continuation. The web view lives in an offscreen borderless window while it prints, and the print operation's view needs a non-zero frame.

## 39. `ContentView.body` Is Near the Type-Checker's Limit
- **Issue**: Adding a few more `.focusedSceneValue` and `.onReceive` modifiers to `ContentView.body` failed the build with "the compiler is unable to type-check this expression in reasonable time".
- **Solution**: Group new modifiers in a small `ViewModifier` (such as `ExportAndWritingCommandsModifier`) and apply it with `.modifier(...)`, rather than extending the chain.

## 40. Sandboxed Apps Can't Read Files Passed on the Command Line
- **Issue**: Launching the app binary directly with a document path (`Swash.app/Contents/MacOS/Swash file.md`) shows "Swash doesn't have permission to read it": only Launch Services grants the sandbox access. `pkill -x Swash` in scripts also quits the user's own copy of Swash.
- **Solution**: Open documents with `open -n -a <app> <file> --args …`, find the new process with `pgrep -n -f <app path>`, and quit only that PID (`scripts/generate_readme_screenshots.sh`). `-appearance light` or `-appearance dark` fixes Light or Dark Mode for one launch (`AppDelegate` reads it from the argument domain and sets `NSApp.appearance`). The older `-NSRequiresAquaSystemAppearance YES` / `-AppleInterfaceStyle Dark` arguments stopped forcing Dark Mode in macOS 27: the app came up light.


## 41. Folder Windows: Watching Subfolders, Links and Headless Snapshots
- **Issue**: A `DispatchSource` file-system source on the folder only reports changes directly inside it, so files added or saved in subfolders went unnoticed. `NSTextView` opens a clicked `.link` with `NSWorkspace`, which can't open a relative URL such as `Other.md`. In headless snapshots (`cacheDisplay`), the `NavigationSplitView` sidebar's material draws as an empty white column even though the list has rows.
- **Solution**: `FolderWorkspace` watches the whole tree with an `FSEventStream` (it works in the sandbox for a folder whose security-scoped access is active) and rescans off the main thread with `FolderScanner` (`FolderIndex.swift`). Folder windows pass a `noteLinkHandler` and a `textRevealRequest` to the editor through the SwiftUI environment rather than through `ContentView`'s parameters (see #39). `SwashTextView.Coordinator` handles `textView(_:clickedOnLink:at:)` and marks `[[wiki]]` links as `swash-note:` links only while a handler is set. Because `SwashTextView.swift` now uses `NoteLinkResolver`, `Swash/FolderIndex.swift` is in every harness's file list (#14). In harnesses, check the sidebar through its `NSTableView` row count, not the snapshot.

## 42. Colour Runs Inside an `NSTextBlock` Make Layout Quadratic
- **Issue**: AppKit finds the extent of a paragraph's `NSTextBlock` (`rangeOfTextBlock:atIndex:`) by walking the text storage's attribute runs, and TextKit 1 does this once per laid-out line. Every syntax-colour run inside a code block therefore slows typing in that block: a 2,000-line JavaScript block went from ~0.7 s to ~2.2 s per keystroke with full colouring. Moving the colours to layout-manager temporary attributes was slower still (each call invalidates display).
- **Solution**: `CodeHighlighter` (`Swash/Markdown/`, Foundation only) tokenizes the whole block in one linear scan; `MarkdownCodeHighlighter.highlight(block:…)` (`Swash/CodeHighlightTheme.swift`, AppKit) colours a block in Edit Text only when it has at most `editorTokenLimit` tokens, and leaves larger blocks plain (the Preview, Quick Look and export still colour them). `Tests/EditorAudit/run_audit.sh perf` checks a 300-line block (coloured, under 100 ms) and a 2,000-line block (plain). `CodeHighlightTheme.swift` is in the explicit `swiftc` lists (GOTCHAS #14).

## 43. Typography Reaches the Editor and Preview as a Value, Not the Environment
- **Issue**: `PreviewScrollView` hosts the preview in its own `NSHostingView`, so SwiftUI environment values set by `ContentView` never reach the blocks. `MarkdownBlockView` is also `Equatable` (compared by source), so a settings change would not re-render unchanged blocks.
- **Solution**: `EditorTypography` (Settings › Appearance) is passed explicitly: `SwashTextView(typography:)`, `MarkdownPreviewView(typography:)` and `MarkdownRenderContext.typography`. It is part of the preview's `contentKey` and of `MarkdownBlockView ==`, and `updateNSView` treats a change like a flavor change (`forceFullRestyle`). The defaults (`EditorTypography()`) must reproduce the original styling exactly; `scaled(_:)` returns the size unchanged at 14 pt. Quick Look has no app group, so it can't read the app's defaults and always uses `EditorTypography()`.

## 44. Checking That Rendering Is Unchanged
- **Issue**: The tracked GFM snapshots were made on another machine, so a local run differs from them in every pixel even when nothing changed (see #8), and can't show whether a change altered the default rendering.
- **Solution**: Make a baseline on the same machine: commit work in progress, check out `origin/main`'s sources, run `scripts/run_spec_tests.sh` (and `run_audit.sh render`), copy `Tests/GFMSpec/snapshots` and `build/editor-audit/render-out` aside, restore your commit, run again and compare the PNGs pixel by pixel (decoded through `CGImage`; the files' bytes differ on every run).

## 45. Format Commands Come From a Generated Manifest
- **Issue**: The Format menu, keyboard shortcuts (`FormatCommand.command(for:)`), bubble-menu labels and tooltips, and the code-block language list are generated from `@pixerate/markdown-conformance`'s `manifest.json`, shared with the Pixerate web editor. Editing labels or shortcuts in `FormatCommands.swift` or `BubbleMenuView.swift` no longer has any effect, and the generated `FormatManifest.generated.swift` is in the PixerateMarkdown package, not here.
- **Solution**: Change the manifest in the Pixerate editor repo (`packages/markdown-conformance/manifest.json`), where `scripts/gen-swift-markdown.mjs` regenerates the Swift and a Swift release ships it; then bump Swash's pin (#63). The generator fails when the manifest names a surface or `enabledWhen` condition that `FormatSurface`/`FormatCondition` (in `FormatManifest.swift`) don't have, or a command id that `FormatCommand(manifestID:params:)` doesn't map; add the case (and, for a condition, its check in `MarkdownFormatting.satisfies(_:selection:)`) in the engine first. Letters in shortcuts match by character and digits/punctuation by ANSI key code (`FormatShortcut.keyCodes`), so shifted keys work on any layout. Swash-only commands (callouts, footnotes, table of contents) stay hand-written. The code-language menu lists the manifest's languages first, with the manifest's labels, then `CodeHighlighter`'s other languages (`CodeFormat.allCases`). The manifest type is `ManifestCodeLanguage`, so it doesn't clash with the highlighter's `CodeLanguage`. The conformance runner fails if a manifest language has no `CodeLanguage`.

## 46. The Conformance Runner Models the Text View's Fallbacks
- **Issue**: `MarkdownEditingCommands.newline`/`indent`/`backspace` return nil when the editor should fall back to the default key behaviour, so comparing their raw result with the shared corpus reports false failures (and hides real ones: Tab on an unnestable list item used to insert a tab character).
- **Solution**: `Tests/MarkdownConformance/ConformanceRunner.swift` applies the `NSTextView` default when an `edit.*` command returns nil (Return inserts `\n`, Backspace deletes, Tab inserts `\t`, Shift-Tab does nothing) and runs Backspace with `markersHidden: true`, as in Edit Text. Intended differences from the corpus go in the runner's `localSkips` with a reason until a `variants.swash` entry lands upstream; the runner warns about local skips that no longer match a case. `FormatCommand`, `FormatCommandEdits` and the manifest types are in `PixerateMarkdown`, and the corpus comes from the same editor checkout, so it always matches the engine's manifest version (#63).

## 47. One Target, Two Platforms: Keep macOS-Only Code Behind `#if os(macOS)`
- **Issue**: The `Swash` app target builds for macOS and iOS (`SUPPORTED_PLATFORMS = iphoneos iphonesimulator macosx`, `SDKROOT = auto`). Every file in the synchronised `Swash/` folder compiles for both platforms, so any new AppKit use breaks the iOS build. Sparkle and the four extensions are macOS-only through `platformFilters = (macos, )` on their build files and target dependencies.
- **Solution**: Wrap AppKit-only files completely in `#if os(macOS)`, and put iOS-only UI in `Swash/iOS/` inside `#if os(iOS)`. Shared code uses `PlatformColor`, `PlatformFont`, `PlatformImage`, `Image(platformImage:)` and `PlatformPasteboard` from `PlatformTypes.swift`. Build both platforms before committing: `-destination 'generic/platform=macOS'` and `-destination 'generic/platform=iOS Simulator'`. The iOS app uses `Swash/Info-iOS.plist` (`INFOPLIST_FILE[sdk=iphone*]`), so document types and URL schemes must be added to both plists.

## 48. `XMLDocument` Is macOS-Only
- **Issue**: `HTMLToMarkdown` parses with Foundation's `XMLDocument` (`.documentTidyHTML`), which iOS does not have. The preview uses it for raw HTML blocks.
- **Solution**: On other platforms the converter uses `HTMLLiteDOM` through file-private type aliases with the same API. Both now live in the `PixerateMarkdown` package (#63), whose `PIXERATE_HTML_LITE` flag runs the lite parser on macOS for tests. Add HTML cases there when changing the converter.

## 49. Offscreen WebKit Rendering on iOS and iPadOS
- **Issue**: Without a viewport meta tag, iOS lays the render page out at 980 px and scales it to the view, so math and diagram snapshots came out cropped. On iPad, desktop-class browsing scaled them down to a fraction of their size. The first render also takes a few seconds while the WebContent process starts.
- **Solution**: `swash-render.html` declares `width=device-width, initial-scale=1` and `-webkit-text-size-adjust: 100%`. On iOS, `RichContentRenderer` sets `preferredContentMode = .mobile`. `UIImage.size` is read-only, so the snapshot is rebuilt with `scale = pixel width ÷ point width`. Check new rendering features on both an iPhone and an iPad simulator.

## 50. SwiftUI Text in Horizontal Scroll Views Under UIKit Hosting
- **Issue**: In the iOS preview (a `UIHostingController` sized by intrinsic content size inside a `UIScrollView`), a multi-line `Text` inside `ScrollView(.horizontal)` was squeezed to one line with an ellipsis.
- **Solution**: Give such text `.fixedSize()` (code blocks), or `.fixedSize(horizontal: false, vertical: true)` where it should wrap.

## 51. Don't Make a UITextView Subclass Its Own Gesture Delegate
- **Issue**: `StyledUITextView` implemented `gestureRecognizer(_:shouldReceive:)` to limit its task-checkbox tap to checkboxes. A scroll view is already the delegate of its own pan and text-interaction recognizers, so the override filtered those too. The editor stopped scrolling, with no error and no `scrollViewDidScroll` calls.
- **Solution**: Give extra recognizers on a text or scroll view a separate delegate object (`TaskTapFilter`). Never implement `UIGestureRecognizerDelegate` methods on the scroll view subclass itself.

## 52. UITextView in UIViewRepresentable Must Fill the Proposed Size
- **Issue**: SwiftUI can size a representable `UITextView` to its fitting size, which is the whole text height, so the view grows instead of scrolling.
- **Solution**: Both iOS editors implement `sizeThatFits(_:uiView:context:)` and return the proposed width and height.

## 53. Edit Text Blocks on iOS: Decorations Instead of NSTextBlock
- **Issue**: iOS has no `NSTextBlock`, which the styler uses on macOS for quotes, alerts, code blocks and rules.
- **Solution**: On iOS, `MarkdownEditorStyler.pushBox`/`pushRule` add a `BlockDecoration` (outermost first) to the context instead. `setParagraphStyle(_ context:…)` sets the paragraph indents for the box's border and padding and writes `.blockDecorations` over the paragraphs. `padBoxes()` turns top and bottom padding into paragraph spacing, and `StyledLayoutManager` paints each box over its paragraphs' line fragments. Always set paragraph styles through `setParagraphStyle(context:…)`. When adjusting a paragraph style later, adjust the indents (`tailIndent -= …`) rather than replacing them, or the box insets are lost on iOS. macOS keeps its `NSTextBlock` path unchanged; check it with `Tests/EditorAudit/run_audit.sh`.

## 54. Default MainActor Isolation and Callbacks on Background Queues
- **Issue**: Every target builds with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`. Closures in a type that isn't marked otherwise are treated as main-actor code, and Swift traps (`EXC_BREAKPOINT`) when a framework calls them off the main thread. The thumbnail extension crashed this way on macOS: Quick Look runs `QLThumbnailReply`'s drawing block on a background queue.
- **Solution**: Mark extension principal classes whose callbacks arrive on background queues `nonisolated` (as `ThumbnailProvider` is), or mark the specific closures `@Sendable`/`nonisolated`. Check new extension points or framework callbacks for the queue they run on.

## 55. ShareLink in a Collapsed Toolbar Menu Crashes on iPhone; Document Share Sheet & Export Activities
- **Issue**: A `ShareLink` in a `.secondaryAction` toolbar item, which collapses into the overflow menu on iPhone, presents `UIActivityViewController` as a popover with no source view. UIKit throws an uncaught `NSGenericException`. Furthermore, sharing only a `.md` file URL caused Apple Notes and Notion to receive no text (Pixerate/Swash#182 / SWA-60), and a separate Export toolbar menu duplicated what users expect from the share sheet (Pixerate/Swash#183 / SWA-61).
- **Solution**: Keep the document's share action in a `.primaryAction` item (`IOSContentView.shareLink`, #73) and hook `UINavigationItem.documentProperties.activityViewControllerProvider` via `DocumentShareBridge` so both the toolbar and the navigation bar title menu present `IOSPresenter.makeDocumentActivityViewController`:
  1. Sharing uses `DocumentShareItemSource` (`UIActivityItemSource`), `UIMarkupTextPrintFormatter` (so the system **Print** action appears automatically), and `applicationActivities`: `ExportPDFActivity`, `ExportHTMLActivity`, `CopyRichTextActivity`, `CopyHTMLActivity`.
  2. For Apple Notes (`com.apple.mobilenotes.SharingExtension`), `DocumentShareItemSource` returns an `NSAttributedString` parsed from `DocumentExporter.clipboardHTML(for:)`, creating a note with rich-text formatting.
  3. For Mail (`.mail`), Messages (`.message`), Notion, and third-party notes/editor apps, it returns plain text Markdown, and supplies the document title as the subject for Mail.
  4. For AirDrop (`.airDrop`) and Save to Files (`.saveToFiles`), it returns the `.md` file URL so the file is transferred or saved with its original name and extension.
  5. `ExportPDFActivity` and `ExportHTMLActivity` asynchronously generate the PDF or HTML file via `IOSDocumentFeaturesModel.export` and present a second share sheet for the generated file.

## 56. Opening Documents From Code on iOS
- **Issue**: SwiftUI's `openDocument` and `newDocument` environment actions are macOS-only. On iOS, `onOpenURL` on a document view doesn't fire while the document browser is showing, and the browser is a presented card on the launch screen but absent from the hierarchy once a document is open. Calling `browser.delegate?.documentBrowser?(browser, didPickDocumentsAt: [url])` on the document browser while another document is open replaces the presented `UIDocumentViewController` without saving or closing the active document, discarding any unsaved edits. Furthermore, switching apps (e.g. into Split View or another app) moves Swash to `.inactive` or `.background`, where `UIDocument` does not automatically flush unsaved changes to disk immediately.
- **Solution**: `DocumentOpener` receives `swash://` URLs in a `UIWindowSceneDelegate` (installed through `@UIApplicationDelegateAdaptor` and `configurationForConnecting`). It finds the browser through `UIDocumentViewController.launchOptions.browserViewController`, which works whether or not a document is open. Before calling `documentBrowser(_:didPickDocumentsAt:)`, `DocumentOpener` checks if the requested URL is already open; if a different document is open, it inspects connected window scenes for active `UIDocumentViewController`s and saves them (`save(to:for: .forOverwriting)`) before delegating to the browser. In `SwashiOSApp`, `.onChange(of: scenePhase)` flushes all open documents using `saveOpenDocumentsOnBackground()` with `UIApplication.shared.beginBackgroundTask` whenever transitioning to `.inactive` or `.background`. Pass files in the app's own Documents folder directly: `revealDocument(at:importIfNeeded: true)` copies them ("Name 2.md").

## 57. iOS Prefers Its Own Quick Look Viewer for Markdown
- **Issue**: iOS has a built-in Markdown previewer and thumbnailer. In Files, they take precedence over a third-party Quick Look preview or thumbnail extension for `net.daringfireball.markdown`, so Swash's extensions registered but never ran.
- **Solution**: The Quick Look and thumbnail extensions are filtered to macOS (`platformFilters = (macos, )`). Only the share extension and widget are built and embedded for iOS.

## 58. Confluence and Jira Copy Images Without an `<img>` Tag
- **Issue**: Atlassian's editor puts each image on the pasteboard as an empty `<div data-node-type="media">` with `data-file-name`/`data-alt` and `data-context-id` (the page ID). There is no `src` and no image data, so a converter that only reads `<img>` drops the images.
- **Solution**: `HTMLToMarkdown.convert(_:sourceURL:)` (in `PixerateMarkdown` since 0.82.0; checks in `scripts/run_paste_tests.sh`) rewrites media nodes as `<img>` before the package converts the HTML. Their source is `https://<site>[/wiki]/download/attachments/<pageID>/<file>`. It takes the site from the `org.chromium.source-url` pasteboard type, which Chromium browsers write. Safari does not write this type, so without it the image keeps only its file name. The attachment needs a signed-in browser, so Swash shows a placeholder for it.

## 59. Don't Re-Identify a View That Declares a Customizable Toolbar
- **Issue**: The folder window first gave `ContentView` an `.id(file)` so each file got fresh editor state. Every switch rebuilt `ContentView`'s `.toolbar(id: "mainToolbar")`, and AppKit threw `NSInternalInconsistencyException` (`index>=0 && index<[_currentItems count]` in `-[NSToolbar _removeItemAtIndex:]`) while SwiftUI removed the old items. A headless `NSHostingView` harness doesn't crash, because it has no window toolbar.
- **Solution**: Keep the view that owns the toolbar stable and reset only the part below it. `ContentView` takes a `documentID` and applies `.id(documentID)` to the editor area, clears its selection state in `onChange(of: documentID)`, and keeps one `ScrollSync` per file (`ScrollSyncStore`). Reproduce toolbar issues in the real app, for example by launching the Debug build binary under `lldb`.

## 60. MacAppKitExtras Is a Separate Module
- **Issue**: `FolderAccessManager`, `DefaultAppManager`, `ScrollSync` and `NestedScrollRouter` live in the local package `Packages/MacAppKitExtras`, not the app target. The swiftc-based runners that compile app sources (`run_spec_tests.sh`, `run_rich_render_tests.sh`, `run_export_tests.sh`, `Tests/EditorAudit/run_audit.sh`) compile app sources directly, so `import MacAppKitExtras` fails unless the module is built first. They also compile without the app's `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, so calling the package's `@MainActor` scroll helpers from an unannotated callback fails there (`call to main actor-isolated instance method ... in a synchronous nonisolated context`) even though the app builds.
- **Solution**: Runners get `EXTRAS="$(scripts/build_mac_appkit_extras.sh)"` and pass `$EXTRAS` to `swiftc`. Annotate app code that calls the package's `@MainActor` APIs explicitly with `@MainActor`. Swash's configuration (the bookmarks defaults key, alert and panel text) is in `Swash/FolderAccessManager.swift` and `Swash/DefaultAppManager.swift` as `static let shared` extensions; keep the `swash_security_scoped_folder_bookmarks` key, or users lose folders they already granted. Run the package's own tests with `swift test --package-path Packages/MacAppKitExtras`.

## 61. Unnamed Dynamic Colours Aren't Equal
- **Issue**: `PlatformColor.appearanceAware(light:dark:)` (an unnamed `NSColor(name: nil)` / `UIColor { traits in … }`) returns a new colour on every call, and two such colours never compare equal. Code that checks `textView.backgroundColor != color` before assigning, or a test that compares against `EditorTheme.paper.background`, then sees a change every time.
- **Solution**: Create each dynamic colour once (a `static let`) and hand out that instance, as `EditorTheme.paperBackground` and `CodeHighlightTheme`'s table do.

## 62. The Outline Is a Split View Column, and SwiftUI's Sidebar Button Clashes Across Windows
- **Issue**: The heading outline was an `HStack` column beside the editor. The unified toolbar didn't know about it, so the window title and toolbar ran across the sidebar's edge. It couldn't simply become a `NavigationSplitView`, because `ContentView` is also the detail of the folder window's split view and split views don't nest. A 3-column split doesn't work either: it can't hide only the middle column (files + editor with the outline hidden). Once document windows had a split view, opening a second document crashed: `NSToolbar … already contains an item with the identifier com.apple.SwiftUI.navigationSplitView.toggleSidebar`. Every window's toolbar is `"mainToolbar"`, AppKit syncs toolbars that share an identifier, and each window added SwiftUI's sidebar button. The bubble harness (`run_audit.sh bubble`), which opens a window per case, crashed the same way.
- **Solution**: `ContentView` wraps its editor in a 2-column `NavigationSplitView` only when it has no `hostedOutline`. It removes SwiftUI's button with `.toolbar(removing: .sidebarToggle)` and keeps its own `"outline"` toggle item. Folder windows pass a `DocumentOutlineState` as `hostedOutline` and show it under an Outline tab in the file sidebar. View › Show Outline acts through the `outlineVisibility` focused value, so each window type decides what it means.

## 63. The Markdown Engine Is the PixerateMarkdown Package
- **Issue**: The parser, renderer, HTML → Markdown converter, code highlighter and the formatting and editing commands used to live in `Swash/Markdown/` and could be changed with the app. They now come from the `PixerateMarkdown` product of the Pixerate editor repo (Swash #50, Pixerate/editor#546), so an engine change made here has nowhere to go, and an engine API that isn't `public` can't be used.
- **Solution**: Change the engine in the editor repo (`packages/swift/Sources/PixerateMarkdown`, with tests in `packages/swift/Tests/PixerateMarkdownTests`), release it (a `v<version>` tag), then bump Swash: Xcode › Package Dependencies, or the `minimumVersion` in `project.pbxproj` and `Package.resolved`. The dependency is `upToNextMinor`, because a 0.x minor can break. `Package.resolved` is committed (`git add -f`, since `project.xcworkspace` is ignored): `scripts/pixerate_markdown.sh` reads the pinned revision from it and fetches the engine, its checks and the conformance corpus into `build/pixerate-editor` (sparse), then builds the module with `swiftc` for every test script. To try engine changes before a release, point the scripts at a local checkout with `PIXERATE_EDITOR_DIR=../editor`, and Xcode at it by dragging the checkout into the project (a local package overrides the remote one). The Quick Look extension compiles the app's sources, so it depends on the product too; Share, Thumbnail and Widget don't use the engine. Sources that use engine types `import PixerateMarkdown`.

## 64. `NSGraphicsContext(bitmapImageRep:)` Returns `nil` for 24-Bit (`samplesPerPixel: 3`) Bitmaps
- **Issue**: Creating an opaque `NSBitmapImageRep` with `samplesPerPixel: 3, hasAlpha: false` (24-bit RGB without a padding byte) succeeds, but `NSGraphicsContext(bitmapImageRep:)` returns `nil` because CoreGraphics `CGBitmapContextCreate` only supports 32-bit RGB formats (`kCGImageAlphaNoneSkipLast` / `kCGImageAlphaNoneSkipFirst`). Drawing into the `nil` context silently no-ops and writes an all-black PNG for `icon_ios_1024.png`.
- **Solution**: Copy the already-opaque 1024 × 1024 source PNG (`samplesPerPixel: 3, hasAlpha: no`) directly to `Swash/Assets.xcassets/AppIcon.appiconset/icon_ios_1024.png` (or strip alpha with `sips -s format png`), rather than re-drawing through `NSGraphicsContext(bitmapImageRep:)` with `samplesPerPixel: 3`.

## 65. iOS Format Surfaces Read the Manifest Too, and the Keyboard Bar Shows Recent Formats
- **Issue**: The iOS formatting bar, the edit menu's Format submenu and the iPadOS Format menu read `FormatManifest` like the Mac (#45), so hand-written labels there have no effect. Manifest 0.2.0 (PixerateMarkdown 0.9.x) puts no command on the `keyboardBar` surface, so `FormatManifest.entries(for: .keyboardBar)` is empty. Some manifest commands (`format.table`) and Swash's own (callout, footnote, table of contents) have no iOS edit: `FormatCommandEdits` returns nil for them.
- **Solution**: The Aa format panel (`FormatPanel` in `Swash/iOS/GlassAccessoryBar.swift`) shows `FormatManifestLayout.formatPanelEntries` (`Swash/iOS/MarkdownEditingTextView.swift`): every iOS-available manifest command from `.menu` (plus any iOS-available non-menu commands), grouped by manifest group. Next to Aa on the keyboard bar sit the user's most recently used format commands (`RecentFormatCommands`, persisted in `UserDefaults`, capped at 6 and seeded with Bold, Italic, Link, Bullet List and Heading 1), rebuilt in place with `UIView.performWithoutAnimation` when recents change and highlighted via `FormatManifestLayout.activeFormats(text:selection:flavor:)`. The edit menu offers the `bubble` entries whose `enabledWhen` holds for the selection. All iOS surfaces drop commands where `FormatCommand.isAvailableOnIOS` is false, and `FormatMenuCommands` shows Callout, Footnote, Markdown Flavor and Table of Contents on macOS only. Icons are the only iOS-side data (`FormatCommand.symbolName`).

## 66. A Second `.toolbar` Inside an iOS Document View Isn't Shown
- **Issue**: The iOS document features (#57) first added their Outline, Document Info and Export items with a `.toolbar` inside a `ViewModifier` applied to `IOSContentView`'s content. The build succeeded, but none of the items appeared: not in the bar, not in the overflow menu. Only the items in `IOSContentView`'s own `.toolbar` (the one next to `.toolbarRole(.editor)`) were shown.
- **Solution**: Put new items in `IOSContentView`'s toolbar builder as a `ToolbarContent` struct (`IOSDocumentToolbar`), and share their state with the modifier that owns the sheets and the outline column through an `@Observable` model (`IOSDocumentFeaturesModel`). Check new toolbar items in the simulator, not just the build.

## 67. Typography on iOS: Dynamic Type and the Preview's Body Size
- **Issue**: The Mac's `EditorTypography` sizes are designed around a 13 pt `.body`. On iOS `.body` is 17 pt, so the preview's non-default path (`.system(size: scaled(13))`) made text *smaller* when the text size went up by one point. The Settings text size and Dynamic Type also have to combine: the styled editor and preview use fixed point sizes, while the source editor uses `UIFontMetrics`.
- **Solution**: `EditorTypography.previewBodySize` is 13 on macOS and 17 on iOS. `IOSTypographySettings.scaled` multiplies the saved text size by the body style's Dynamic Type scale (`UIFontMetrics.scaledValue(for: 17)/17`, exactly 1 at the default Large size), so default settings at the default size reproduce the original look; it goes to `StyledTextView(typography:)` and `MarkdownPreviewView(typography:)`. `SourceTextView(textSize:)` takes the unscaled size, because its `UIFontMetrics` font applies Dynamic Type itself. `StyledTextView` restyles fully when the typography changes and centres a readable column with `textContainerInset` from `layoutSubviews`.

## 68. iOS Editor Tests: Programmatic Typing Skips the Delegate, and the Test Target Is iOS-Only
- **Issue**: `UITextView.insertText(_:)` and `deleteBackward()` called from code don't ask `textView(_:shouldChangeTextIn:replacementText:)`; the keyboard asks first and only then inserts. Tests that type this way never reach the Edit Text editor's structural editing (Return list continuation, Backspace-unformat, the "/" menu), the iOS counterpart of GOTCHAS #16. The editor's first styling pass is scheduled with `DispatchQueue.main.async`, and the first editor in a process can take over a second to get there, so a fixed short run-loop pump leaves the storage unstyled. Rich-text paste is limited: the HTML that UIKit writes for RTF styles bold and italic with CSS classes (`span.s2 {font-weight: bold}`), which `HTMLToMarkdown` doesn't read, so pasted RTF keeps its links but loses bold and italic.
- **Solution**: `Tests/SwashiOSTests/EditorHarness.swift` hosts the real `StyledTextView` in a `UIHostingController` in a window of the test host app, asks the delegate before each `insertText`/`deleteBackward` as the keyboard does, waits for `Coordinator.fullPassCount > 0`, and runs Tab/Shift-Tab through the view's `keyCommands`. The "/" menu is forced to its compact form (`traitOverrides.horizontalSizeClass = .compact`) so its `BlockMenuBar` buttons can be triggered. The `SwashiOSTests` target (`SDKROOT = iphoneos`, `TEST_HOST` = the app) is only in the scheme's test action, so `xcodebuild build` for macOS is unaffected, but `xcodebuild test` must use an iOS Simulator destination: `xcodebuild test -scheme Swash -destination 'platform=iOS Simulator,name=iPhone 17' CODE_SIGNING_ALLOWED=NO`. Its folder is a synchronised group, so new test files need no project edits. Compare styling passes with `EditorHarness.fingerprint()`, which resolves colours for a fixed appearance (GOTCHAS #61). Programmatic `insertText` isn't an undoable change, and UIKit clears the undo history when it happens: a test that checks undo must undo before typing anything more. On a real keyboard, typing is undoable and the history stays.

## 69. Agent Tools: Same Names as the Web Editor, Raw-Markdown Positions, and Who Links PixerateCore
- **Issue**: The agent tools (#49) must keep the Pixerate web editor's tool names and argument schemas (`createRichTextToolProvider` / `createDocumentFormatTools` in the editor repo's `packages/core/src/agent/`) so agents and the `pixerate-*` skills work unchanged, but their positions are raw-Markdown UTF-16 offsets, not ProseMirror positions. `get_range` is the web editor's *spreadsheet* tool, not a text tool, and `set_text_align`/`edit_table` have no Markdown equivalent yet. `ContentView` hooks the tools up, and the Quick Look extension compiles `ContentView`, so it needs the `PixerateCore` product too (both targets list it; the app's build file is filtered to macOS). Handlers are `AgentToolHandler` closures: in this target they are inferred `@MainActor`, so `MainActor.assumeIsolated` inside them warns ("unavailable from asynchronous contexts") — call main-actor code directly.
- **Solution**: Keep tool logic in `Swash/MarkdownAgentTools.swift` (Foundation, PixerateCore and PixerateMarkdown only, behind the small `MarkdownToolTarget` protocol), and the app side (`AgentBridge.swift`: sessions, the embedded `LocalMCPServer`, the `AgentToolsHookup` modifier) separate. Writes go through `SwashEditorController.applyAgentEdit`, which breaks undo coalescing around `apply` so each call is one undo step (GOTCHAS #10). Add schema properties only when copying them from the web editor. `scripts/run_agent_tools_tests.sh` compiles the tools with the app's concurrency flags (`-swift-version 5 -default-isolation MainActor` plus the approachable-concurrency features); `scripts/pixerate_core.sh` builds `PixerateCore` from the pinned editor revision and adds it to older sparse checkouts of `build/pixerate-editor`. In a swiftc runner's `main.swift`, top-level code without `await` is not main-actor isolated in Swift 5 mode: use top-level `await` or wrap it in `MainActor.assumeIsolated`. For an end-to-end check, launch a Debug build with `-agentBridgeEnabled YES -agentBridgePort …` (and optionally `-agentBridgeToken …`) launch arguments, which override `@AppStorage` without saving, and POST JSON-RPC to the embedded server (see the `swash-build-test` skill).

## 70. Slack mrkdwn Is Parsed Onto the Shared Model, and Its Delimiters Are Written Swash-Side
- **Issue**: The engine (`PixerateMarkdown`) only speaks CommonMark/GFM: its inline parser reads `*x*` as emphasis and `<https://a|b>` as one autolink, and `MarkdownFormatting.toggle` writes `**`, `*` and `~~`. Slack documents used to get a separate regex styler on the Mac and no Edit Text or formatting on iOS (#56).
- **Solution**: `SlackMarkdown.parse` (Swash/SlackMarkdown.swift) runs the engine's block parser, turns HTML blocks into paragraphs (Slack has no HTML; `<!here>` at a line start is otherwise an HTML block), and replaces the inline children of paragraphs, headings and cells with Slack nodes that carry ranges and markers like the engine's. `MarkdownEditorStyler`, `isActive`, removal and block toggles then work unchanged. Anything that *adds* syntax must go through the flavour-aware wrappers: `MarkdownDocument.parse(_:flavor:)`, `MarkdownFormatting(text:flavor:)`, `FormatCommandEdits.edit(for:…flavor:)`, `.link(…flavor:)` and `.activeLink(…flavor:)`, and `setSlackLink`. Never call `formatting.toggle(.strong…)` or `setLink` directly for a document that might be Slack, and key any cached parse on the flavour as well as the text (`SwashEditorController`, `Coordinator.formatting(for:flavor:)`). On iOS the edit menu checks `enabledWhen` against `IOSEditorController.flavor`, which `IOSContentView` keeps in step with the document. `scripts/run_slack_tests.sh` checks both; `SlackMarkdown.swift` is in every runner's file list (#14).

## 71. UIKit Can't Turn Off Spell-Checking for Part of a Text View
- **Issue**: On the Mac, `SwashTextView` keeps spelling underlines out of code through `NSTextView` delegate and spelling-state APIs. `UITextView` has only the view-wide `spellCheckingType` trait: no per-range hook, no public attribute that exempts text, and `UITextChecker` only reports misspellings; it can't control the view's underlines. So code blocks and spans get spelling underlines in the iOS editors (#58).
- **Solution**: Left as is on purpose. The workarounds are hacks: switching `spellCheckingType` as the caret enters code (it applies to the whole view, still underlines code while the caret is elsewhere, and needs `reloadInputViews`), or turning system checking off and drawing our own underlines from `UITextChecker` (loses the system Replace… suggestions, Learn/Ignore Spelling and language detection). Revisit if UIKit adds a per-range API.
- **Table cells**: The iOS cell editor is a `UITextView` (`IOSCellTextView` in `InteractiveTableView.swift`) styled by `CellMarkdownStyler`, which the Mac's `CellTextView` uses too. Restyling skips while `markedTextRange` is set, because replacing attributes cancels keyboard composition. A SwiftUI `.toolbar(placement: .keyboard)` doesn't appear for a UIKit text view, so the cell's Previous/Next/Done bar is its `inputAccessoryView`.

## 72. iOS Editors Under the Navigation Bar Get No Top Safe Area
- **Issue**: For text to scroll under the iOS 26 navigation bar (transparent header, scroll-edge effect), the UIKit editors must ignore the top safe area. Once they do, their `safeAreaInsets.top` is 0, and so is a `GeometryReader`'s `proxy.safeAreaInsets.top` when it ignores the safe area too. Content then starts under the bar.
- **Solution**: `IOSContentView` measures the gap as the global `minY` of a `Color.clear` that respects the safe area minus the editor's `minY`, then passes it as `topInset`. `UIScrollView.setTopBarInset(_:)` (in `PlatformTypes.swift`) applies it as `contentInset.top` on `SourceTextView`, `StyledTextView` and `PreviewScrollView`. `ScrollSync` already includes `adjustedContentInset.top`.

## 74. `NSHostingView.fittingSize` Measures SwiftUI Content at Its Ideal Width
- **Issue**: The macOS `PreviewScrollView` sized its document view from `hostingView.fittingSize.height`. SwiftUI answers `fittingSize` at the content's *ideal* width, where paragraphs don't wrap (for example 1,935 pt instead of the 783 pt shown), so a document with long paragraphs measured far too short. Setting the frame width first, or adding a temporary width constraint, makes no difference. The hosting view then centred the overflowing content, so the start and the end of the document were cut off with no way to scroll to them. It showed most in Quick Look, where documents open at a fixed panel width.
- **Solution**: The hosted root view is `PreviewScrollView.MeasuredContent`: the content with `.fixedSize(horizontal: false, vertical: true)`, top-aligned, which reports its laid-out height with `onGeometryChange`. `fit(_:in:coordinator:)` uses that height (`Coordinator.contentHeight`), and a change in height (images loading, rendered formulas) refits the document view. Don't go back to `fittingSize` for wrapping SwiftUI content.

## 75. iOS Keyboard Bars: Glass, Scrolling, and UIButton Titles From Actions

Aa swaps `inputView` for `FormatPanelInputView` (Notes-style panel). `resignFirstResponder` clears it, so the keyboard returns next time.

## 76. A NavigationSplitView Inside DocumentGroup Gets a Second Navigation Bar

## 78. The Writing Partner Acts After the Change, and Undo Must Put the Caret Back
- **Issue**: The writing partner (#61) fixes the word or paragraph the person just finished. `shouldChangeTextIn` sees the typed character before the change lands, and in Edit Text the styled storage isn't the Markdown (GOTCHAS #9, #20). Its fix must also be an undo step of its own: merged into the person's typing, ⌘Z would remove their word along with it. After ⌘Z, `NSTextView` selects the restored word, so the next keystroke lands inside it. Unclosed code spans and inline math (`` `dont `` while it's being typed) aren't code or math to the parser yet.
- **Solution**: `WritingPartnerSession` (Swash/WritingPartnerSession.swift, shared by macOS and iOS since #109; see #102) notes a boundary character in `shouldChangeTextIn` (only for the person's typing: not while `isApplyingEdit`, restyling, SwiftUI updates, Writing Tools, marked text or undo/redo), then runs on the next run-loop turn after `textDidChange`. It reads the raw Markdown and caret through the coordinator, asks `PunctuateVoice` (Swash/WritingPartner.swift: an adapter onto the editor package's `TextMechanics` checks in PixerateMarkdown, Pixerate/editor#892, which hold the rules and are specified by shared scenarios in `@pixerate/conformance`) for fixes, and applies them with `applyEdit` between two `breakUndoCoalescing()` calls, with the action name "Punctuation". An `NSUndoManagerDidUndoChange` observer checks `redoActionName == "Punctuation"` to count the undo against the fix's rules, then puts the caret back where it was on the next turn, after the restyle. The voice treats an odd number of backticks or dollar signs earlier on the line as code or math still being typed. Each boundary's raw offset is recorded when it's typed, with whether an Enter was at the end of its line, because a fast typist's next keys can land before the run-loop turn: fixes are worked out per boundary, in order, on the text the earlier fixes left. The session sets `inlinePredictionType = .no` while it's on: macOS's inline predictive text also writes at the caret, and the two together left words like `dont't`. Swash shows each line on its own, so the voice treats the start of a line as the start of a sentence, and Enter at the end of a line of four or more words as its end, though a single newline is only a soft break to Markdown. What the partner shows is `WritingPartnerOverlay` (Swash/WritingPartnerOverlay.swift): an `NSView` subview of the text view that ignores hits and draws only in layers, so it never changes the text or the undo stack. It sweeps a gradient over `PunctuateVoice.checkedRange`, and the partner's cursor plays each fix out word by word (see #79). Boundaries typed meanwhile wait for the fix and move with each word it changes. With Reduce Motion there's no sweep and each word lands at once. The partner takes over autocorrect: while it's on, the text view's `isAutomaticSpellingCorrectionEnabled` is off (saved and restored when it's off again), and its Spelling rule asks `NSSpellChecker.correction(forWordRange:in:language:inSpellDocumentWithTag:)` instead; both together lost fixes (the partner's edit cancelled the system's pending correction, `teh` → `Teh`). It's on by default (not following the system's "Correct spelling automatically", which people often turn off because macOS autocorrect is hard to undo; the partner's fixes are undo steps that learn). Interaction tests that check punctuation set it off, because what the system spell checker corrects depends on the Mac (it stops correcting words whose corrections were reverted). Undoing a spelling fix calls `ignoreWord(_:inSpellDocumentWithTag:)` rather than counting against the rule. Text replacement stays on (the user's list has entries such as `(r)` → ® that aren't words), so it can change a word while a fix is on its way: every change the person (or macOS on their behalf) makes while a fix plays moves the fix's boundaries and words with it, and a fix whose word changed under it is worked out again once, on the new text. `its` → `it's` uses `NLTagger`'s word class for the next word (adverb, determiner, verb or pronoun). `id` and `ill` are tagged themselves, in their line once the next word is finished: as a pronoun or verb they become `I'd` and `I'll`; as a noun or adjective they stay (the tagger's class for the *next* word is unreliable there: "like" in "id like" comes back as an interjection). A comma goes before "but" only when the clause before it has a verb and the word after it starts a clause (pronoun, determiner, preposition or adverb), and not after words that make "but" mean "except" ("nothing but"). Any runner that compiles `SwashTextView.swift` must also compile `WritingPartner.swift`, `WritingPartnerSession.swift` and `WritingPartnerOverlay.swift`. Before #229, in **Suggest** mode (#103, `WritingPartnerMode.suggest`, now read as Copyedit), `punctuate` worked out the same `PartnerEdit`s without applying them, draws a subtle tint and underline in `WritingPartnerOverlay.suggestionLayers` (`showSuggestions`), announces the suggestion to VoiceOver (`NSAccessibility.Notification.announcementRequested` and `lastAnnouncement`), and exposes a `"Suggestions"` rotor in `MarkdownRotorDelegate`. Suggestions can be accepted by clicking the word, pressing Tab or ⌥⏎ while the caret is at/just after it, or choosing Edit › Accept Suggestion (which plays the fix through `AgentTextDirector` as its own undo step), and dismissed with Esc or by finishing the line, or typing on well past it, without accepting it (which counts against the rule like an undo); editing the suggested word itself removes the suggestion without penalty. In the Slack flavour (`WritingPartnerVoice.chat`, #105) the editor's `chat` profile plays: apostrophes, capital `I` and spelling only, never chat shorthand (`lol`, `idk`) or case-only corrections, never Slack syntax (`<@user>`, `<!here>`, `:emoji:`), and no typography. Its learned weights are stored under `WritingPartnerDefaults.chatStats`, apart from prose (`WritingPartnerDefaults.stats`). Words inside Slack `*bold*` markers aren't reached yet (Pixerate/editor#899). `scripts/run_writing_partner_eval.sh` (#106) runs the strip-and-restore evaluation across `Tests/WritingPartnerEval/corpus` against `Tests/WritingPartnerEval/baseline.json` (with `--update-baseline` to refresh the baseline), `scripts/run_writing_partner_tests.sh` checks the voice by typing text one character at a time, and the `writing-partner-*` cases in `Tests/EditorAudit/InteractionRunner.swift` check it in the real editor (see #109 below for levels since #229).

## 79. The Writing Partner's Typing Is Drawn, Not Written, Until Each Word Lands
- **Issue**: The partner's cursor plays its fixes through the editor package's `AgentTextDirector` (PixerateCore, #878): it selects a word, types the new one in frames, then commits it as one undo step. A host normally shows those frames by writing them into the text outside the undo history. In an `NSTextView` that breaks undo: the person keeps typing while the partner plays, and `NSTextView` records their keystrokes at offsets that include a half-typed word, which no longer fit once it's replaced. Written frames would also reach `textDidChange`, which publishes (and autosaves) the half-typed word.
- **Solution**: `WritingPartnerTarget` (in Swash/WritingPartnerSession.swift) is the director's `AgentTextTarget`. Its `agentText` is the raw Markdown with the word being typed (`ghost`) in place of the word it replaces, and `previewAgentTyping` only changes `ghost`; `WritingPartnerOverlay` covers the old word and draws the typed one in its font, with the cursor at its end. Only `commitAgentEdit` touches the text, through `applyEdit` between two `breakUndoCoalescing()` calls, so every word the partner changes is its own "Punctuation" undo step. `willType` reports each of the person's edits to `WritingPartnerTarget.personWillEdit` and `AgentTextDirector.noteEdit` (moving the ghost, the director's range and the fix's remaining words); undo or redo cancels the fix, and the director puts nothing back because nothing was written. `PunctuateVoice.partnerEdits` turns a fix into whole-word edits, left to right, each with the rules of the voice edits it covers, so undoing one word counts against only its rules. The session isn't `@MainActor` (the swiftc runners compile the editor in Swift 5 mode, where `SwashTextView.Coordinator` isn't on the main actor); its director calls run on the main actor. Runners that compile `WritingPartnerSession.swift` must source `scripts/pixerate_core.sh` and link `$PIXERATE_CORE`. Interaction tests wait for `writingPartner.isIdle` (`waitForPartner`) rather than a fixed time.

Check the demo's timing with the Browser pane visible: in a hidden pane `IntersectionObserver` and animation frames don't run, so it never starts. ## 83. Foundation Models On-Device Bandleader & Swift Concurrency Isolation
- **Issue**: Integrating Apple's on-device `FoundationModels` framework requires `@available(macOS 26.0, *)` and `#if canImport(FoundationModels)`. ## 85. Typography: Curly Quotes Is a Switch, Dashes and Ellipses Are Learned

## 86. Web Pages Can Reach the Embedded MCP Server on 127.0.0.1
- **Issue**: A page in any browser can POST to `http://127.0.0.1:4477/mcp`. A `text/plain` POST needs no CORS preflight, and DNS rebinding can make a foreign host name resolve to 127.0.0.1. The token is optional, so without checks any website could call the document tools.
- **Solution**: The server is PixerateCore's (`MCPServerController`, editor 0.81.0+). `MCPHTTP.isAllowed` refuses (403) a request whose `Host` isn't this machine, whose `Origin` is present and not local, or a POST that isn't `application/json`, as the MCP Streamable HTTP transport requires. The server never answers a preflight with CORS headers. Reject a negative or oversized `Content-Length` before slicing the body, or `subdata` traps.

## 87. Widget Web Views Need a Navigation Lock, Not Just a CSP
- **Issue**: A GenUI `widget` block runs agent-supplied HTML/JS in a `WKWebView`. Its CSP (`default-src 'none'`) blocks fetches and remote images, but CSP doesn't govern navigation: `location = …`, a link click, a form submit or a meta refresh can load any site in the document, or send the widget's data out in a URL. And every unsaved document has the trust key `"untitled"`, so allowing one would allow them all, permanently.
- **Solution**: `WidgetNavigationLock` allows only the app's own `loadHTMLString` (about:blank, main frame) and cancels every other navigation. Widget web views use a non-persistent data store and can't open windows. `WidgetTrustManager` never trusts the unsaved-document key: the placeholder asks you to save the document first.

## 88. The Embedded MCP Server Can't Announce Tool-List Changes
- **Issue**: The embedded server (PixerateCore's `MCPHTTPServer`) answers each POST with plain JSON and refuses `GET` (no SSE stream), so it can't send `notifications/tools/list_changed`, and clients list tools once when they connect. Building `tools/list` from the open documents meant an agent that connected before any document was open (the server starts at launch) saw only `list_documents` until it reconnected, and one that connected while the frontmost document was read-only never saw the write tools.
- **Solution**: `tools/list` always returns the full catalogue from a document-less, editable `AgentDocumentSession` (`AgentBridge.catalog`, passed to PixerateCore's `MCPToolRouter` as its `catalog`). A write tool called on a read-only document returns a "read-only" error instead of the registry's "Unknown tool"; the router does this when a session's `target.readOnlyReason` is set. Calls without a `document` argument go to the document whose window was most recently active (`AgentToolsHookup` watches `appearsActive`), not the one opened last.

## 89. Embedded MCP Server: Failed Listeners, 401s and Protocol Versions
- **Issue**: An `NWListener` that fails (for example `EADDRINUSE`) stays allocated until cancelled, and cancelling it reports `.cancelled`, which overwrote the failure in Settings with "Stopped". A 401 on every path, `/.well-known/oauth-protected-resource` included, sends MCP clients looking for an OAuth server that doesn't exist. Clients on MCP 2025-06-18 send `MCP-Protocol-Version` on every request.
- **Solution**: PixerateCore's `MCPHTTPServer` detaches a failed listener before cancelling it (so the failure stays visible), sets `hasFailed`, and `AgentBridge.settingsChanged` (`MCPServerController.update`) restarts a failed server. Unknown paths return 404 before the token check; a bad token returns 401 with `WWW-Authenticate: Bearer` and is compared in constant time. `supportedProtocolVersions` drives both `initialize` negotiation and the `MCP-Protocol-Version` check (400 for an unsupported one). Settings › Agents flags ports outside `MCPHTTP.validPorts`.

## 90. The Embedded MCP Server Moved Off Port 4477
- **Issue**: Swash's server defaulted to 4477, the port `pixerate-mcp-bridge` (`toolBridgeDefaultPort`) listens on, so running the bridge for another Pixerate app (JazzPaint) made Swash's server fail with "Port 4477 is in use", or the other way round.
- **Solution**: `AgentBridgeDefaults.defaultPort` is 4478. `MCPServerController` has no shared default, so each app picks its own. `AgentBridgeDefaults.migrateStoredPort()` (run when `AgentBridge` starts) stores 4477 for people who had the server on with no port saved, so the MCP config they already copied keeps working; everyone else gets 4478.

## 91. The swiftc Test Scripts Break on a Checkout Path With Spaces
- **Issue**: `scripts/run_agent_tools_tests.sh`, `Tests/EditorAudit/run_audit.sh` and the other runners fail with "no such module 'PixerateCore'" (or `PixerateMarkdown`) when the checkout lives under a path with a space (e.g. `~/Development/Claude Worktrees/…`).
- **Solution**: `$PIXERATE_CORE` / `$PIXERATE_MARKDOWN` are swiftc flags expanded unquoted so they split into words, which also splits `-I <path>` at the space. Run the scripts from a symlink without spaces (`ln -s "<checkout>" /tmp/swash && cd /tmp/swash`): the scripts use `$PWD`, which keeps the symlink's path.

## 92. UIKit's `NSLayoutManager` Has No Temporary Attributes for Focus Mode
- **Issue**: On macOS, Focus Mode dims text outside the current paragraph or sentence with `NSLayoutManager.addTemporaryAttribute` / `removeTemporaryAttribute`, which doesn't touch `NSTextStorage`. UIKit's `NSLayoutManager` doesn't have temporary attributes, and writing dimmed foreground colours into `NSTextStorage` on every caret move would trigger full restyles and alter the editor's styling fingerprint.
- **Solution**: `StyledLayoutManager` (`Swash/iOS/StyledLayoutManager.swift`) holds `focusedCharacterRange: NSRange?` and dims glyph runs, list markers, badges and alert icons outside that range to `unfocusedAlpha` (`0.3`) inside `drawGlyphs(forGlyphRange:at:)` and `drawBackground(forGlyphRange:at:)`. Changing the focused range only calls `invalidateDisplay(forCharacterRange:)`, keeping `NSTextStorage` untouched.

## 93. `#Preview` Bodies Compile in Release Builds
- **Issue**: Wrapping preview-only helpers (sample documents, `PreviewModifier`s in `Swash/PreviewModifiers.swift`) in `#if DEBUG` breaks the Release build with "cannot find 'SwashSampleDocument' in scope": the `#Preview` macro expansion is not stripped from Release, so every symbol a preview references must exist in all configurations.
- **Solution**: Keep shared preview helpers unconditional and small, or wrap both the helper and every `#Preview` that uses it in `#if DEBUG`. Build the Release configuration (as `PR Build` does) after touching previews.

## 94. A Shared `LanguageModelSession` Refuses Overlapping Requests and Fills Up
- **Issue**: The on-device bandleader keeps one `LanguageModelSession` per document across pauses (SWA-30). `LanguageModelSession` throws if `respond` is called while it `isResponding`, and a timed-out or cancelled pause can still be unwinding when the next one starts. Every exchange is also kept in its transcript, and the on-device context window is small (about 4,096 tokens), so a long-lived session overflows; a refused or failed exchange stays in the transcript and colours later pauses.
- **Solution**: `OnDeviceWritingBandleader.currentOrNewSession()` hands out a one-off session while the shared one is still answering, and starts a fresh shared session after `maxTurnsPerSession` exchanges. Any error or cancellation discards the shared session; `exceededContextWindowSize` retries the pause once on a fresh one. The session lives on `WritingPartnerSession.activeBandleader` (one per editor), and `resetBandleaderSession()` drops it when the editor's document URL changes or the partner is paused, so one document's text never reaches another's prompts.

## 95. Agent Presence: Each Agent Has Its Own Selection, and Its Closures Must Not Retain the Session
- **Issue**: Showing MCP agents' carets inline (#151, #152) means agents can't use the user's selection: `set_selection` and agent edits used to move the user's caret. Each agent's selection must move with every edit (the user's typing, undo, the writing partner, other agents), and an agent's stale positions must be mapped through edits made since it read them, or refused when they overlap one. Mapping the user's typing needs `SwashEditorController.onUserRawEdit`, which the controller holds — and the session's closures already hold the controller, so capturing the session strongly there leaks both per window.
- **Solution**: `AgentDocumentSession` (Swash/MarkdownAgentTools.swift, so `scripts/run_agent_tools_tests.sh` can test it) keeps one selection per `ToolActor.id`, seeded from the user's cursor the first time it is asked for. Every edit is a revision (`revision`, `revisionHistory`, the tools' `baseRevision`); `MarkdownToolProvider.resolveRange` maps or refuses stale positions. Its `carets` (PixerateCore's `AgentCaretStore`) is the only presence state: `SwashEditorController.agentCarets` hands it to `WritingPartnerOverlay.attachExternal`, which draws each agent in its colour with a name tag. `AgentCaretStore.mapThroughEdit` maps one edit at a time in the current text and leaves a caret at an insertion point where it is, so map multi-edit changes last-first and put heads back on the session's selections. `applyAgentEdit` maps the user's selection through the agent's raw edits. The hookup installs `onUserRawEdit` (a per-keystroke diff) only once an agent appears (before that the session diffs the text on the next tool call), captures the session and editor weakly, and clears it on disappear or when the document changes. Each tool call is one undo step named after its agent ("Insert Text (Claude Code)"); NSUndoManager has no per-agent undo.

## 96. MCP Calls Are Attributed to the Client That Initialized Last
- **Issue**: PixerateCore's `MCPHTTPServer` passes its handler only `(method, params)` and uses one `Mcp-Session-Id` for every client, so Swash can't tell which connected client made a `tools/call`.
- **Solution**: On `initialize`, `AgentBridge.actor(forInitialize:)` sets `router.actor` from `clientInfo` (`mcp:<name>`, so a reconnecting client keeps its caret and colour). Calls are attributed to the most recently initialized client: two clients connected at once share one caret until PixerateCore passes request headers (per-client session ids) to the handler. The per-agent selections, carets and revisions already work for distinct actors.

## 97. The Formatting Voice Tidies Blocks the Person Edited, After the Caret Leaves, and Checks the Rendering
- **Issue**: The Formatting voice (#113) fixes Markdown, not words, so it can't run at word boundaries like the Punctuate voice: a list being typed would be renumbered under the caret, and tidying a whole document on open would rewrite text nobody touched. Some fixes look harmless but change what CommonMark renders (`*_foo_*` restyled to `**foo**`, a trailing space inside a code span that crosses a line, two adjacent lists with different bullets). Multi-line fixes (a table, a blank line) can't be typed through the partner's cursor a word at a time.
- **Solution**: `WritingPartnerSession.formattingDirty` keeps the raw ranges the person changed (moved with every edit, cleared on undo and redo). On a caret move, after punctuation and after a fix finishes, `tidy` asks `FormattingVoice.edits` (Swash/FormattingVoice.swift) for fixes to the top-level blocks those ranges touch, except the caret's block, which includes the line just after it (one Enter hasn't left a list yet; a blank line has). The voice works on the parsed AST (`MarkdownDocument.root.children`), never inside code, math, HTML or front matter, and checks its own work: fixes of rules meant to keep the rendering (spacing, emphasis style, tables) are dropped if `MarkdownHTMLRenderer` output (whitespace runs collapsed) would change. `scripts/run_writing_partner_tests.sh` also runs those rules over every CommonMark and GFM spec example without that check (`verify: false`) and fails if any rendering changes. Fixes become `PartnerEdit`s with the undo name "Formatting" (the undo observer counts it like "Punctuation"), and `playsInstantly` when they span lines. The rules are `PunctuationRule` cases (`isFormatting`) so stats and ⌘Z learning are shared, but they're left out of the bandleader's `JazzTextVoiceState`. Off for Slack; since #229 on in Source view too (`formattingInSource` is only cleared by `adoptLearnedDefaults`). Any runner that compiles `WritingPartner.swift` must also compile `FormattingVoice.swift`.

## 98. On-Device Context Spelling: the Model Names Words, Swash Finds Them
- **Issue**: Context-aware spelling (#98) comes from Apple's on-device model through the bandleader, which only runs on macOS 26 with Apple Intelligence. Small models count characters badly, so offsets in their replies (as the grammar corrections use) often point at the wrong word; and the model happily "corrects" capitals, names and words the writer uses on purpose.
- **Solution**: `OnDeviceSpellingCorrection` (Swash/OnDeviceWritingBandleader.swift) asks for the word as written, its correction, its kind (misspelling or wrong word) and a confidence. `ContextSpelling.suggestions` (Swash/WritingBandleader.swift, testable without FoundationModels) finds the word whole and exactly once in the paragraph, drops case-only changes, rewrites of more than two words, misspelling fixes too far from the word, and anything below `offerThreshold` (0.5), and marks `applyAtOnce` at `applyThreshold` (0.85). They become `.spelling` / `.wrongWord` `JazzTextSuggestion`s, so `BandleaderSuggestionPlanner` plays them like Pixerate's (#120): made at once or offered, undo ignores the word. The planner also skips a `.spelling` fix whose word recurs in the document (`ContextSpelling.recurs`). Tests can't construct the `@Generable` types below macOS 26, so they feed `ContextSpellingCandidate`s through `StubWritingBandleader`. `scripts/run_context_spelling_eval.sh` needs the real model and prints SKIP without it.

## 99. Marks Are Suggestions That Wait: Keep Them Out of Suggest Mode's Dismissal Rules
- **Issue**: Marks (#128) reuse Suggest mode's drawing and its accept and dismiss mechanics (#103), but Suggest mode dismisses a suggestion, and counts it against its rule, when the person finishes the line or types well past it. A mark must survive typing, and it can sit far from the caret for a long time while edits move it.
- **Solution**: Marks live in `WritingPartnerSession.marks` (`PartnerUncertainMark`, logic in Swash/PartnerMarks.swift so the partner test runner covers it) and are drawn by `WritingPartnerOverlay.showMarks` as dotted lines, not as suggestions. Only the mark being settled is turned into a `Suggestion`, tagged with its `markID`: typing elsewhere drops that suggestion silently (the mark stays), Esc routes through `dismissSuggestion` to `keep(markID:)` (one penalty, and `keptMarks` stops the word being marked again), and an accepted candidate is a normal fix whose commit removes the mark in `moveMarks`. `willType` moves marks before its undo/redo early return; an edit by the person that reaches into a mark settles it their way. `applyBandleaderResponse` turns `offeredEdits` (planner and pause-tier grammar) and unsure structural suggestions into marks when `WritingPartnerDefaults.suggestions` (#229, the old `markUncertain` key) is on, and drops them when it's off; a later fix the partner is sure of removes an overlapping mark. A suggestion with `alternatives` is never applied at once. The count reaches the status bar through `SwashEditorController.onPartnerMarksChange` (set in `ContentView.onAppear`, to keep `ContentView.body` under the type-checker's limit, GOTCHAS #39). Runners that compile `WritingPartnerSession.swift` must also compile `PartnerMarks.swift`.

## 100. Build Folders Next to `build/` Get Committed as Broken Submodules
- **Issue**: Building into folders such as `build-appstore/` or `build-test-repro/` leaves SwiftPM package checkouts there, each with its own `.git`. Only `build/` was ignored, so committing everything recorded those checkouts as gitlinks with no `.gitmodules` entry. CI then warned `No url found for submodule path …`, and `git status` failed locally with `fatal: bad object HEAD`. Swash Pro (#169) also lost its real changes this way: GitHub Desktop stashed them when the branch was switched, and the commit picked up only the test change and the gitlinks, so the account tests failed and the changeset was missing.

Before pushing, check `git show --stat HEAD` for the files you expect, and if GitHub Desktop says it stashed changes, restore them (`git stash list`) before committing.

## 101. Mac App Store Builds Leave Out Sparkle (`Release-AppStore`)
- **Issue**: The Mac App Store rejects apps that bring their own updater (Sparkle) or ask for Sparkle's Mach lookup exceptions (`-spks`, `-spki`). Deleting `Sparkle.framework` from the app in a run script phase doesn't work: Xcode embeds and signs package frameworks as separate tasks that can run after the script, and a script phase that has no declared inputs isn't ordered against them (the framework comes back, or code signing fails on the deleted bundle). Xcode also only generates the Info.plist keys it knows from `INFOPLIST_KEY_*` settings, so `INFOPLIST_KEY_SUFeedURL` and the like produce nothing.
- **Solution**: The `Release-AppStore` build configuration and the `Swash (App Store)` scheme keep Sparkle out:
  1. The app target's `EXCLUDED_SOURCE_FILE_NAMES` lists `SparkleUpdater.swift`, `Sparkle` and `Sparkle.framework`. The setting applies to every build phase, so Sparkle is neither compiled against, linked nor embedded. `SWIFT_ACTIVE_COMPILATION_CONDITIONS` adds `APP_STORE`, update UI in `SettingsView` and `SwashApp` sits inside `#if !APP_STORE`, and `APP_STORE` also fixes `PixerateAccess.defaultDistributionMode` to the App Store (#169).
  2. Sparkle's keys stay in `Swash/Info.plist` for direct builds. The `Strip Sparkle Keys (App Store Builds)` phase deletes them from the processed Info.plist; its input path, the built Info.plist, makes it run after Info.plist is processed, and `ENABLE_USER_SCRIPT_SANDBOXING = NO` in this configuration lets it edit that file.
  3. It signs with `Swash/Swash-AppStore.entitlements`, which has no Sparkle Mach lookup exceptions.
  4. `scripts/verify_app_store_build.sh <path to Swash.app>` checks the result. The PR build runs it on the macOS build and also builds the scheme for the iOS Simulator.

## 102. The Writing Partner's Session Is Shared: Hosts Work in Raw Offsets
- **Issue**: The writing partner (#61) was written against `NSTextView` and `SwashTextView.Coordinator`. iOS (#109) has two editors with their own offsets (Edit Text maps storage to raw Markdown; Source's text is the Markdown) and no `NSSpellChecker`, inline-prediction switch or `NSAccessibility`. UIKit has no autocorrection API: `UITextChecker` only gives guesses. Its `ignoreWord` is per checker, like a document tag. Turning the keyboard's autocorrect off takes effect only after `reloadInputViews()`. `PixerateAccess.post` used URLSession's default 60 s timeout, so a dropped connection held up the pause tier for a minute before `leadWithFallback` reached the on-device partner. The interaction runner's `preview-nested-scroll-routing` case waited a fixed 0.3 s for the preview's code block and table to lay out, which takes 0.3–0.5 s on a busy Mac.
- **Solution**: The session talks only to `WritingPartnerHost` and `WritingPartnerCanvas` (Swash/WritingPartnerHost.swift), and every offset in them is raw Markdown. The Mac host is `MacWritingPartnerHost` (Swash/WritingPartnerMacHost.swift). The session's `textView:coordinator:` methods there keep `SwashTextView`'s call sites unchanged. iOS uses `IOSWritingPartnerHost` (Swash/iOS/IOSWritingPartner.swift), set up by each editor's coordinator with closures for raw ↔ storage offsets and for applying an edit. Its spelling takes the checker's first guess only within two edits, and its canvas is `IOSWritingPartnerOverlay`, a subview of the text view that takes touches only on its notes. On iOS, Enter and structural Backspace return `false` from `shouldChangeTextIn` after a structural edit, so the coordinator calls `didChange` itself. The partner's own edits set `isApplyingPartnerEdit`, so they aren't reported as typing. Pausing is kept in `IOSEditorController.partnerPaused`, so switching between Source and Formatted keeps it. Tab and Esc (`MarkdownEditingTextView.keyCommands`) and the edit menu (`writingPartnerMenu`) accept or dismiss suggestions. `PixerateCore` is linked on iOS too (its build file has no platform filter). Pause requests pass `timeout: PixerateWritingBandleader.leadTimeout` (6 s). The preview test waits for the outer document to be taller than the window. `Tests/SwashiOSTests/WritingPartnerTests.swift` covers typing, undo, pausing and the fallback. It skips the `NLTagger` word-class check on the Simulator, which gives no classes (Pixerate/editor#893), and runs it on a device.

## 103. Isolated Deinits Crash on the iOS Simulator: Mark Editor Classes' Deinits `nonisolated`
- **Issue**: With `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, a class's deinit can run through `swift_task_deinitOnExecutorImpl`. On the iOS 26.3.1 Simulator with Xcode 26.3, freeing such an object from the main thread outside a task (a `DispatchQueue.main.async` styling pass, a test harness tearing down) aborts with `malloc: pointer being freed was not allocated` in `TaskLocal::StopLookupScope::~StopLookupScope`. Every `SwashiOSTests` case that hosts the editor crashed, while CI, on its own toolchain, passed them.
- **Solution**: Classes created and released while the iOS editors run have `nonisolated deinit` (with a comment pointing here). These are `MarkdownEditorStyler`, `BlockDecoration`, `IOSEditorController`, both editors' coordinators, the iOS preview's coordinator, `StyledLayoutManager`, `IOSDocumentFeaturesModel`, the writing partner's session, target, host and overlay, and `EditorHarness`. Give a new class on that path one too. A nonisolated deinit can't touch main-actor state: `WritingPartnerSession.undoObserver` is `nonisolated(unsafe)` (it's only set on the main thread). `IOSWritingPartnerOverlay` drops its caret subscription in `didMoveToSuperview` instead of in its deinit. An empty `nonisolated deinit {}` isn't dead code: deleting it brings the crash back.

## 104. Context-Spelling Eval: Slow, Nondeterministic, Confidence Not Calibrated

## 106. `AppEnum` Conformances on `nonisolated` Enums Need `nonisolated extension`

## 108. Flavour Detection on Open Picked Slack for GitHub Markdown

## 109. Writing Partner Levels, Learned-by-Default Rules and Edit Layers (#229)
- **Issue**: The partner's `off`/`suggest`/`automatic` modes, a switch per grammar and formatting rule, Spelling and "Also in Source view" made Settings long, and the partner's fixes could only be taken back with ⌘Z, which also undid any typing after them.
- **Solution**: `WritingPartnerMode` is `.off`, `.copyedit` (default) and `.ghostwrite`. Its custom `init?(rawValue:)` reads the old `automatic` and `suggest` as Copyedit, and `migrateExistingInstall` (macOS launch) / `SwashAppDelegate` (iOS) rewrite the stored value. Ghostwrite sends `engagementMode: ghostwrite` in `JazzTextLeadRequest` (absent means copyedit to an older server, Pixerate/schemas#87) and makes a structural suggestion it is sure of at once, on the Ghostwrite layer (`acceptActiveSuggestion(layer:)`); Copyedit only offers it, and only with Suggestions on. Suggestions (`WritingPartnerDefaults.suggestions`, the old `markUncertain` key) gates marking low-confidence fixes; off, they're dropped. There are no rule switches left in Settings except Curly quotes: `isRuleEnabled` still honours the old keys as hidden overrides because the interaction tests turn Spelling off (GOTCHAS #78), and `adoptLearnedDefaults` clears them once (`learnedDefaultsAdopted`) so nobody keeps an invisible "off". Copyedit's auto-formatting is the Formatting voice's `formatTitleLines` rule (Swash/FormattingVoice.swift): a short, unpunctuated, markup-free top-level line set apart by blank lines and followed by a longer paragraph or a list becomes `#`/`##` (or the previous heading's level); greetings and sign-offs are skipped; it changes the rendering on purpose, so it is in `mayChangeRendering` and left out of the spec-rendering check. Emphasis and context-dependent structure stay server-side. Edit layers live in `WritingPartnerSession.layers` (`EditLayerStack`, Swash/EditLayers.swift, Foundation only so the partner runner tests it): `committed` records each partner edit with `PartnerEdit.layer`, `willType` moves them through the person's typing (an edit the person types into leaves its layer), and `revertEdits`/`revertLayer` validate against the current text, apply the reverts last-first as one undo step ("Revert Copyedit"), and count them against the rules like ⌘Z. Layers are never saved and are cleared by `documentDidChange()` (which replaced the editors' `resetBandleaderSession()` calls on a document change). The UI is `WritingPartnerEditsView` (Edit › Writing Partner Edits… ⇧⌥⌘E on the Mac, the document menu on iOS). Any runner that compiles `WritingPartner.swift` must also compile `EditLayers.swift`. The Partner style preview plays `WritingPartnerPreviewScript.script(for:)` per level; on iOS it is `IOSWritingPartnerStylePreviewView` (Flair is now linked on iOS: its build file has no platform filter), and the iOS editor's overlay draws them too (GOTCHAS #110).

## 110. Flair Treatments in the iOS Editor Overlay
- **Issue**: `IOSWritingPartnerOverlay` is a subview over the text, so it can't draw a treatment's `behind` layers (fills, bands) under the glyphs; a `CADisplayLink` retains its target, so a link targeting the overlay keeps it alive; and system colours (`systemPurple`, the text and page colours) differ in Dark Mode, so values resolved once go stale.
- **Solution**: The overlay stages the treatment like the Mac's `WritingPartnerOverlay` (`checking`, `caret`, `selecting`, `typing`, `landed`) and puts `renderer.aboveLayer` in its own layer but inserts `renderer.behindLayer` at index 0 of the text view's layer: above the text view's background, below the subview that draws the glyphs, and in the same content coordinates since the overlay sits at the origin. It drives frames with a `CADisplayLink` through a weak `DisplayLinkProxy`, stops it (and removes `behindLayer`) when nothing plays or the overlay leaves its text view, resolves colours against the text view's `traitCollection`, and drops its cached look on a `UITraitUserInterfaceStyle` change. `IOSWritingPartnerOverlay.look(id:traits:)` is shared with the Settings preview so the two match. The old `ghostLabel`/`caretLayer` are gone: `isShowingGhost`, `ghostText` and `isShowingCaret` now report what the last frame planned.


## 111. Custom Title and Metal Drawing on the iOS Document Manager
- **Issue**: Drawing the site's hero wordmark (Flair `swash-text`) over the `DocumentGroup` launch screen hit several traps. `DocumentGroupLaunchScene` ignores a `Text` title's font and colour (`.foregroundStyle(.clear)` still painted it), a `nil` title falls back to the app's name, and `actions` are turned into system buttons, so a custom view there shows as a button labelled with its text. `DocumentLaunchGeometryProxy.titleViewFrame` is the whole area above the browser card (title and buttons), in window coordinates, while `overlayAccessoryView` is laid out inside the safe area. On the Metal side, `UIGraphicsImageRenderer`'s default (`.automatic`) range gives an extended-range image on wide-colour screens that `MTKTextureLoader` refuses (no error unless you catch it, just no texture), and Flair shaders end by un-premultiplying (`c.rgb / c.a`), so drawn straight into a `CAMetalLayer` their faint glow composites as white halos. Passing a `CGImage` as an effect's texture input (`.cgImage`/`.image`) re-uploads it with mipmaps every frame.
- **Solution**: `SwashiOSApp` passes a blank title (`Text(verbatim: " ")`), which keeps its row so Create Document stays put, and draws `SwashLaunchWordmark` (Swash/iOS/IOSSwashWordmark.swift) in `overlayAccessoryView` with `.ignoresSafeArea()`: baseline at `titleViewFrame.midY` minus a scaled 10pt (where the system title was), centred across `titleViewFrame` as the site's hero is. The canvas is an `MTKView` driven by a `CADisplayLink` through a weak proxy; it renders the words once per text, size and appearance with `format.preferredRange = .standard`, loads them with `MTKTextureLoader` (`.origin: .flippedVertically`, mipmaps, as Flair's textures have row 0 at the bottom) and binds them with `FlairRenderer.setLiveTexture(_:for: "uText")`, and renders with `blendOver: true`, which blends over the cleared drawable and so premultiplies. As on the site, the plain `Text` shows until the shader's first frame and under Reduce Motion, and the canvas is the words' box divided by `uSize` (0.6) so the shader's letters sit on the plain ones.
